# Requirements Document

## Introduction

This spec covers the platform foundation of the card checkout store: the monorepo layout, code-quality tooling, test coverage gates, the continuous integration pipeline, the architectural dependency rule, the base AWS infrastructure defined as Terraform, a minimal deployed web skeleton, and the `GET /api/v1/health` endpoint reachable through CloudFront. It implements the base part of HU-17 ("Deploy to the cloud") and the applicable non-functional requirements RNF-02, RNF-03, RNF-14 and RNF-15, plus the repository and cost constraints from the steering files.

Business features (catalog, checkout, payments) are out of scope. The goal is a green pipeline and a public HTTPS URL where the web skeleton is served and `/api/v1/health` answers, so later user stories can be built and deployed on top.

Decisions fixed for this spec:

- `web/` contains a minimal deployed skeleton (Vite, React 18, Redux Toolkit, one placeholder page, Jest tests, build). It is uploaded to S3 to verify CloudFront and the SPA rewrite.
- Terraform uses remote state in a versioned, encrypted, private S3 bucket with S3 native locking (`use_lockfile`), without a DynamoDB lock table. The `infra/bootstrap` module is the only exception: it uses local state, which is ignored by git.
- Deployment is automatic through GitHub Actions against the Developer's AWS account. The workflow `deploy.yml` authenticates with OIDC (no long-lived AWS access keys in GitHub), runs when the CI_Pipeline finishes successfully for a push to `master` (`workflow_run`) and on manual dispatch, and applies only after a manual approval on the GitHub Environment `production`.
- The only manual infrastructure step of the Developer is a one-time apply of `infra/bootstrap`, which creates the state bucket, the GitHub OIDC provider and the deploy role. Before the first deploy, the Developer also creates the three Payment_Secret_Parameters in SSM with the AWS CLI; Terraform never manages or reads them.
- Terraform does not manage the three payment secrets: it only knows their parameter names (for the Lambda environment and the IAM policy), so their values never enter the Terraform state or plan. The Origin_Verify_Secret is generated by Terraform. No real secret passes through GitHub Actions, lives in the repository, or is uploaded as a workflow artifact.
- Runtime is Node.js 22 LTS everywhere (local, CI and Lambda `nodejs22.x`); `nodejs20.x` is no longer a supported Lambda runtime.
- Non-secret values needed by the workflow are stored as GitHub repository or environment variables, not as secrets.
- The origin guard is implemented now: the API answers 403 when the `X-Origin-Verify` header is missing, including on `GET /api/v1/health`. CloudFront adds the header on requests to the Lambda.
- Agents never run `terraform apply` or `terraform destroy`, never commit or push, and never call the payment provider with real keys. Apply runs only inside `deploy.yml` after approval, and no workflow runs `terraform destroy`.

## Glossary

- **Monorepo**: The single Git repository containing `api/`, `web/`, `infra/`, `docs/`, `scripts/` and `.github/workflows/`.
- **API**: The NestJS backend in `api/`, using the Express adapter, bundled for AWS Lambda.
- **Web_App**: The React 18 single-page application in `web/`, built with Vite, using Redux Toolkit.
- **Web_Skeleton**: The minimal Web_App delivered by this spec: one placeholder page, a Redux store, Jest tests and a production build.
- **Domain_Layer**: The code in `api/src/domain`, which holds entities, value objects and domain errors.
- **Health_Endpoint**: The route `GET /api/v1/health` of the API.
- **Origin_Guard**: The API component that validates the `X-Origin-Verify` header against the secret read from SSM.
- **Origin_Verify_Secret**: The shared secret stored in an SSM SecureString parameter, injected by CloudFront as the `X-Origin-Verify` header on requests to the Lambda Function URL.
- **Distribution**: The single CloudFront distribution that serves the Web_App from S3 and routes `/api/*` to the Lambda Function URL.
- **SPA_Rewrite_Function**: The CloudFront Function attached to the S3 behavior that rewrites extension-less paths to `/index.html`.
- **Web_Bucket**: The private S3 bucket holding the Web_App build, readable only by the Distribution through Origin Access Control (OAC).
- **Lambda_Function**: The AWS Lambda (Node.js 22, 512 MB, 15 s timeout) running the API behind a Function URL.
- **Infra_Code**: The Terraform configuration in `infra/`.
- **Quality_Gates**: The checks lint, type check, tests with coverage threshold, build and secret scan.
- **CI_Pipeline**: The GitHub Actions workflow in `.github/workflows/` that runs the Quality_Gates.
- **Coverage_Threshold**: A Jest `coverageThreshold.global` of 80 for statements, branches, functions and lines.
- **Dependency_Rule**: The `dependency-cruiser` rule that forbids the Domain_Layer from importing NestJS, the AWS SDK or HTTP libraries.
- **Forbidden_Words_Check**: The script `scripts/check-forbidden-words.sh`, which reads `.kiro/private/forbidden-words.txt` and reports any forbidden word found in the repository.
- **Budget_Alarm**: The AWS budget alert set at 1 USD.
- **Developer**: The human who runs the one-time Bootstrap_Module apply, configures the GitHub Environment and variables, approves deployments, replaces the payment secret placeholders in SSM, commits and pushes.
- **Bootstrap_Module**: The Terraform module in `infra/bootstrap` that uses local state and creates the State_Bucket, the GitHub_OIDC_Provider and the Deploy_Role.
- **State_Bucket**: The private S3 bucket that stores the remote Terraform state of `infra/`, with versioning, server-side encryption and all public access blocked.
- **GitHub_OIDC_Provider**: The IAM OpenID Connect identity provider for GitHub Actions in the AWS account.
- **Deploy_Role**: The IAM role that `deploy.yml` assumes through the GitHub_OIDC_Provider, limited to this repository and to the `master` branch or the `production` environment.
- **Deploy_Pipeline**: The GitHub Actions workflow `.github/workflows/deploy.yml`.
- **Production_Environment**: The GitHub Environment named `production`, configured with required reviewers.
- **Deploy_Variables**: The GitHub repository or environment variables (not secrets) used by the Deploy_Pipeline: Deploy_Role ARN, AWS region, State_Bucket name, `budget_notification_email`, `payment_api_url` and the payment public key (a public value). The Web_Bucket name, Distribution id and Lambda_Function name come from Terraform outputs.
- **Payment_Secret_Parameters**: The three SSM SecureString parameters `/<project_name>/payment/private-key`, `/<project_name>/payment/integrity-secret` and `/<project_name>/payment/events-secret`, created and updated only by the Developer with the AWS CLI. Terraform references them by name only.
- **Smoke_Test**: The `curl` checks that the Deploy_Pipeline runs against the Distribution after deployment.

## Requirements

### Requirement 1: Monorepo layout and TypeScript baseline

**User Story:** As a developer, I want a monorepo with a fixed layout and strict TypeScript, so that every later user story lands in a predictable place.

#### Acceptance Criteria

1. THE Monorepo SHALL contain the top-level directories `api/`, `web/`, `infra/`, `docs/`, `scripts/` and `.github/workflows/`.
2. THE API SHALL contain the source directories `api/src/domain`, `api/src/application/ports`, `api/src/application/use-cases`, `api/src/infrastructure/http`, `api/src/infrastructure/persistence`, `api/src/infrastructure/payment` and `api/src/infrastructure/config`.
3. THE API SHALL contain the entry files `api/src/main.ts` and `api/src/lambda.ts`.
4. THE Web_App SHALL contain the source directories `web/src/app`, `web/src/features/product`, `web/src/features/checkout`, `web/src/features/transaction` and `web/src/shared`.
5. THE API and THE Web_App SHALL each compile with TypeScript `strict: true`.
6. THE Monorepo SHALL contain no `.js` files holding application logic.
7. THE API and THE Web_App SHALL each declare Node.js 22 LTS as the required runtime in `package.json` `engines` and in an `.nvmrc` file.
8. THE API and THE Web_App SHALL each expose the npm scripts `lint`, `test`, `build` and `typecheck`.
9. THE Monorepo SHALL contain a `.env.example` file that lists variable names only and no values for secrets.
10. THE Monorepo SHALL list `.env`, `*.tfstate`, `*.tfstate.*`, `.terraform/` and `.kiro/private/` in `.gitignore`.

### Requirement 2: Linting and formatting (RNF-14)

**User Story:** As a developer, I want ESLint and Prettier enforced in both projects, so that the code stays clean and a failing style check blocks the pull request.

#### Acceptance Criteria

1. THE API and THE Web_App SHALL each provide an ESLint configuration in the flat config format (`eslint.config.mjs`) and a Prettier configuration. Legacy `.eslintrc*` files SHALL NOT be used, because ESLint v10 no longer reads them.
2. WHEN `npm run lint` runs inside `api/` or `web/` on the committed code, THE lint command SHALL finish with exit code 0 and zero errors.
3. WHEN a source file violates a Prettier formatting rule, THE lint command SHALL report an error and finish with a non-zero exit code.
4. THE ESLint configuration of THE API SHALL report an error for the explicit `any` type in files under `api/src/domain`.
5. WHEN `npx tsc --noEmit` runs inside `api/` or `web/`, THE TypeScript compiler SHALL finish with exit code 0.

### Requirement 3: Jest tests with an 80% coverage threshold

**User Story:** As a developer, I want Jest configured with a global 80% coverage threshold in both projects, so that coverage cannot silently fall below the rubric limit.

#### Acceptance Criteria

1. THE API SHALL run unit tests with Jest using `ts-jest` or `@swc/jest`, and THE Web_App SHALL run unit tests with Jest using `ts-jest` or `@swc/jest` and React Testing Library.
2. THE Jest configuration of THE API and of THE Web_App SHALL set `coverageThreshold.global` to 80 for statements, branches, functions and lines.
2a. THE Jest configuration of THE API and of THE Web_App SHALL collect coverage from every source file under `src/` (`collectCoverageFrom`), so that a file without tests counts as uncovered instead of being omitted from the report.
3. IF any of the four coverage metrics falls below 80 in `api/` or `web/`, THEN THE Jest command `npm test -- --coverage` SHALL finish with a non-zero exit code.
4. THE Jest configuration of THE API SHALL exclude from coverage only `main.ts`, `lambda.ts`, wiring-only Nest modules, type-only files and the seed script.
5. THE Jest configuration of THE Web_App SHALL exclude from coverage only `index.tsx`, `main.tsx` and type-only files.
6. WHEN `npm test -- --coverage` runs on the committed code, THE API and THE Web_App SHALL each report at least 80 for statements, branches, functions and lines.
7. THE API SHALL include tests for the Health_Endpoint and the Origin_Guard that run with supertest against the Nest application.
8. THE Web_App SHALL include tests that render the placeholder page and exercise the Redux store.

### Requirement 4: Dependency rule for hexagonal architecture (RNF-15)

**User Story:** As a developer, I want an automated rule that keeps the domain free of framework code, so that the hexagonal architecture is enforced and not only documented.

#### Acceptance Criteria

1. THE Monorepo SHALL provide a `dependency-cruiser` configuration that implements the Dependency_Rule for `api/src/domain`.
2. IF a file under `api/src/domain` imports `@nestjs/*`, `@aws-sdk/*`, `express`, `axios`, `node-fetch` or another HTTP library, THEN THE dependency-cruiser check SHALL report an error and finish with a non-zero exit code.
3. IF a file under `api/src/domain` imports from `api/src/application` or `api/src/infrastructure`, THEN THE dependency-cruiser check SHALL report an error and finish with a non-zero exit code.
4. WHEN the dependency-cruiser check runs on the committed code, THE dependency-cruiser check SHALL finish with exit code 0.
5. THE API SHALL expose the dependency-cruiser check as an npm script so that THE CI_Pipeline can run it.

### Requirement 5: Continuous integration pipeline

**User Story:** As a developer, I want a CI pipeline that runs all quality gates on every pull request, so that a broken change cannot be merged.

#### Acceptance Criteria

1. WHEN a pull request is opened or updated, or a commit is pushed to `master`, THE CI_Pipeline SHALL run.
2. THE CI_Pipeline SHALL run, for each of `api/` and `web/`, the steps lint, `npx tsc --noEmit`, `npm test -- --coverage` and build, using Node.js 22.
3. THE CI_Pipeline SHALL run the dependency-cruiser check for `api/`.
4. THE CI_Pipeline SHALL run gitleaks over the repository history checked out by the workflow.
5. THE CI_Pipeline SHALL run the Forbidden_Words_Check WHERE the forbidden words file is available to the runner; WHERE it is not available (GitHub-hosted runners, because the file is git-ignored), the step SHALL be skipped with a visible notice, and the local git hooks of Requirement 18 remain the enforcing guard.
6. IF any step of THE CI_Pipeline finishes with a non-zero exit code, THEN THE CI_Pipeline SHALL mark the run as failed.
7. THE CI_Pipeline SHALL cache npm dependencies between runs.
8. THE CI_Pipeline SHALL grant the workflow only the `contents: read` permission.
9. THE CI_Pipeline SHALL contain no secret values, no AWS credentials, no OIDC role assumption and no Terraform plan or apply step.
10. WHEN a pull request is opened or updated, THE Monorepo SHALL run only the CI_Pipeline and SHALL NOT run the Deploy_Pipeline.

### Requirement 6: Secret handling and repository rules (RNF-02)

**User Story:** As a security-conscious developer, I want secrets kept out of the repository and out of the web bundle, so that a leak cannot expose payment credentials.

#### Acceptance Criteria

1. THE Monorepo SHALL store the payment private key, the integrity secret, the events secret and the Origin_Verify_Secret only in SSM Parameter Store SecureString parameters when deployed, and only in the git-ignored `.env` file when running locally.
2. WHEN gitleaks scans the repository, THE CI_Pipeline SHALL report zero findings.
3. THE `.env.example` file SHALL contain the backend variable names `PAYMENT_API_URL`, `PAYMENT_PUBLIC_KEY`, `PAYMENT_PRIVATE_KEY_PARAM`, `PAYMENT_INTEGRITY_SECRET_PARAM`, `PAYMENT_EVENTS_SECRET_PARAM`, `ORIGIN_VERIFY_SECRET_PARAM`, `BASE_FEE_IN_CENTS`, `DELIVERY_FEE_IN_CENTS` and the DynamoDB table names, and the frontend variable names `VITE_API_BASE`, `VITE_PAYMENT_API_URL` and `VITE_PAYMENT_PUBLIC_KEY`.
4. WHEN the Web_App production build completes, THE Web_App bundle SHALL contain no occurrence of the string `prv_` and no value of any SSM parameter.
5. THE Monorepo SHALL contain no occurrence of any word listed in `.kiro/private/forbidden-words.txt` in code, tests, fixtures, comments, documentation, specs, Terraform files or workflow files, and SHALL use the generic term `payment` for the provider.
6. WHEN `bash scripts/check-forbidden-words.sh` runs on the Monorepo, THE Forbidden_Words_Check SHALL report no findings.
7. THE Web_App SHALL expose through Vite only variables whose names start with `VITE_`.

### Requirement 7: API runtime configuration

**User Story:** As a developer, I want the API to validate its configuration at startup, so that a misconfigured deployment fails fast instead of failing on the first request.

#### Acceptance Criteria

1. WHEN the API starts, THE API SHALL validate the environment variables `PAYMENT_API_URL`, `PAYMENT_PUBLIC_KEY`, `PAYMENT_PRIVATE_KEY_PARAM`, `PAYMENT_INTEGRITY_SECRET_PARAM`, `PAYMENT_EVENTS_SECRET_PARAM`, `ORIGIN_VERIFY_SECRET_PARAM`, `BASE_FEE_IN_CENTS`, `DELIVERY_FEE_IN_CENTS` and the DynamoDB table names.
2. IF a required environment variable is missing or has an invalid format, THEN THE API SHALL fail startup with an error message that names the variable and does not print any variable value.
3. THE API SHALL default `BASE_FEE_IN_CENTS` to 300000 and `DELIVERY_FEE_IN_CENTS` to 800000 WHERE the variables are not set.
4. THE API SHALL return configuration validation failures as `Result` values from the configuration module, and SHALL throw only at the application entry point.
5. THE API SHALL read the Origin_Verify_Secret value from the SSM parameter named by `ORIGIN_VERIFY_SECRET_PARAM` once per Lambda cold start and reuse the value for later invocations.

### Requirement 8: Health endpoint

**User Story:** As an evaluator, I want `GET /api/v1/health` to answer through CloudFront, so that I can confirm the API is alive and warm the Lambda before testing.

#### Acceptance Criteria

1. WHEN a request `GET /api/v1/health` carries a valid `X-Origin-Verify` header, THE API SHALL respond with status 200 and a JSON body containing `status` equal to `ok`.
2. THE Health_Endpoint SHALL respond without calling DynamoDB, SSM at request time, or the payment provider.
3. THE API SHALL prefix every route with `/api/v1`.
4. THE API SHALL include an `X-Request-Id` header in every response, and SHALL reuse the incoming `X-Request-Id` value WHERE the request provides one.
5. WHEN `GET https://<distribution-domain>/api/v1/health` is requested over HTTPS, THE Distribution SHALL return the API response with status 200.
6. THE Health_Endpoint response SHALL contain no stack trace, no environment value and no secret.

### Requirement 9: Origin guard

**User Story:** As a security-conscious developer, I want the API to reject any request that did not come through CloudFront, so that nobody can call the Lambda Function URL directly.

#### Acceptance Criteria

1. IF a request reaches the API without the `X-Origin-Verify` header, THEN THE Origin_Guard SHALL respond with status 403, including for `GET /api/v1/health`.
2. IF a request reaches the API with an `X-Origin-Verify` header whose value differs from the Origin_Verify_Secret, THEN THE Origin_Guard SHALL respond with status 403.
3. WHEN a request carries an `X-Origin-Verify` header equal to the Origin_Verify_Secret, THE Origin_Guard SHALL pass the request to the route handler.
4. THE Origin_Guard SHALL compare the header value with the Origin_Verify_Secret using a constant-time comparison.
5. THE Origin_Guard 403 response SHALL use the error format `{ "statusCode": 403, "code": "FORBIDDEN_ORIGIN", "message": <text>, "details": [] }` and SHALL contain neither the expected secret nor the received header value.
6. THE Origin_Guard SHALL apply to every route of the API, so that later routes such as the payment events webhook are protected by the same guard.
7. IF the Origin_Verify_Secret cannot be read from SSM at startup, THEN THE API SHALL fail startup and write a log entry that names the parameter and omits any value.

### Requirement 10: Lambda packaging and runtime

**User Story:** As a developer, I want the API packaged as a small Lambda bundle that initializes once, so that cold starts stay short and the cost stays at zero.

#### Acceptance Criteria

1. WHEN `npm run build` runs inside `api/`, THE build SHALL produce a single bundled `lambda.js` artifact using esbuild on the output of the TypeScript compiler (or with a decorator-metadata plugin), so that the NestJS decorator metadata (`emitDecoratorMetadata`) is preserved in the bundle.
1a. WHEN the bundled `lambda.js` handler is invoked locally with a Function URL event for `GET /api/v1/health` carrying a valid `X-Origin-Verify` header, THE handler SHALL return status 200, proving that dependency injection works inside the bundle.
2. THE `lambda.ts` handler SHALL initialize the Nest application once per Lambda container and reuse the instance across invocations.
3. THE Lambda_Function SHALL run on the Node.js 22 runtime (`nodejs22.x`) with 512 MB of memory and a 15-second timeout.
4. THE Lambda_Function SHALL be exposed through a Lambda Function URL.
5. THE API SHALL write structured JSON logs that include the request identifier.
6. THE API SHALL return error responses without stack traces.

### Requirement 11: Web skeleton

**User Story:** As a developer, I want a minimal web application deployed from day one, so that CloudFront routing and the SPA rewrite are verified before the real screens are built.

#### Acceptance Criteria

1. THE Web_Skeleton SHALL use React 18, Vite as the bundler only, Redux Toolkit with a configured store, and CSS Modules or SCSS.
2. THE Web_Skeleton SHALL render one placeholder page with a visible title written in Spanish.
3. WHEN `npm run build` runs inside `web/`, THE Web_Skeleton SHALL produce a static build with hashed asset file names.
4. THE Web_Skeleton SHALL render without horizontal scroll at viewport widths from 375 px to 1440 px.
5. THE Web_Skeleton SHALL read the API base path from `VITE_API_BASE`, with the value `/api/v1`.
6. THE Web_Skeleton SHALL contain no Next.js, Angular or Vue code and no heavy UI kit.
7. THE Web_Skeleton SHALL include a Redux store module under `web/src/app` and tests that run under Jest.

### Requirement 12: Terraform base infrastructure (HU-17 base)

**User Story:** As an evaluator, I want the cloud infrastructure created from code in the repository, so that the public environment is reproducible.

#### Acceptance Criteria

1. THE Infra_Code SHALL define all resources in `infra/` using Terraform, with the AWS provider region set to `us-east-2`.
2. THE Infra_Code SHALL configure the Terraform `s3` backend in `us-east-2` with `use_lockfile` enabled, encryption enabled, and the State_Bucket as the target, and SHALL NOT define a DynamoDB lock table.
2a. THE `.gitignore` SHALL exclude `*.tfstate`, `*.tfstate.*` and `.terraform/`, including the local state of the Bootstrap_Module.
3. THE Infra_Code SHALL define the Web_Bucket as a private S3 bucket with all public access blocked and access granted only to the Distribution through OAC.
4. THE Infra_Code SHALL define one Distribution whose default behavior serves the Web_Bucket and whose `/api/*` behavior forwards to the Lambda Function URL with caching disabled.
5. THE Infra_Code SHALL attach the SPA_Rewrite_Function to the default behavior of the Distribution, and SHALL NOT configure custom error responses on the Distribution.
6. THE Infra_Code SHALL configure the Distribution to redirect HTTP requests to HTTPS and to use the default `*.cloudfront.net` certificate.
7. THE Infra_Code SHALL define the Lambda_Function with the Node.js 22 runtime (`nodejs22.x`), 512 MB of memory, a 15-second timeout and a Function URL.
7a. THE Infra_Code SHALL attach to the Lambda_Function a resource-based policy that allows both `lambda:InvokeFunctionUrl` (with `FunctionUrlAuthType` `NONE`) and `lambda:InvokeFunction` (restricted to invocations through the function URL), because function URLs created since October 2025 require both permissions.
8. THE Infra_Code SHALL define five DynamoDB tables (products, customers, transactions, deliveries and idempotency keys), all in provisioned capacity mode with auto scaling and point-in-time recovery disabled.
9. THE Infra_Code SHALL provision DynamoDB capacity as products 2 RCU and 1 WCU, customers 2 RCU and 2 WCU with a GSI `email` of 1 RCU and 1 WCU, transactions 3 RCU and 3 WCU with a GSI `reference` of 1 RCU and 1 WCU, deliveries 2 RCU and 2 WCU, and idempotency keys 1 RCU and 2 WCU, for a total of 12 RCU and 12 WCU.
10. THE Infra_Code SHALL enable TTL on the idempotency keys table using the attribute `expiresAt`.
11. THE Infra_Code SHALL define one SSM Parameter Store standard SecureString parameter, encrypted with the AWS managed key, for the Origin_Verify_Secret, and SHALL reference the three Payment_Secret_Parameters by name only (Lambda environment variables and IAM resource ARNs).
11a. THE Infra_Code SHALL NOT declare an `aws_ssm_parameter` resource or data source for the Payment_Secret_Parameters, so that their values never enter the Terraform state or plan.
11b. THE Infra_Code SHALL generate the Origin_Verify_Secret with the Terraform `random_password` resource.
12. THE Infra_Code SHALL define the CloudWatch log group of the Lambda_Function with a retention of 7 days.
13. THE Infra_Code SHALL grant the Lambda_Function an IAM role with least privilege: read access to the four SSM parameters, access to the five DynamoDB tables and their indexes, and write access to its own log group.
14. THE Infra_Code SHALL NOT define API Gateway, VPC, NAT Gateway, RDS, Secrets Manager, WAF, Route 53, load balancers, or DynamoDB on-demand tables.
15. THE Infra_Code SHALL pass `terraform fmt -check` and `terraform validate`.
16. THE Infra_Code SHALL expose the Distribution domain name, the Web_Bucket name and the Lambda_Function name as Terraform outputs.

### Requirement 13: Origin verification wiring and security headers (RNF-02, RNF-03)

**User Story:** As a security-conscious developer, I want CloudFront to add the origin secret and the security headers in one place, so that the API stays private and responses carry the required headers.

#### Acceptance Criteria

1. THE Infra_Code SHALL configure the `/api/*` behavior to send the custom origin header `X-Origin-Verify` with the Origin_Verify_Secret value to the Lambda Function URL origin.
2. THE Infra_Code SHALL obtain the Origin_Verify_Secret value from the `random_password` resource, and SHALL mark the value as sensitive in Terraform outputs.
3. THE Infra_Code SHALL attach a CloudFront Response Headers Policy to the Distribution that sets `Strict-Transport-Security`, `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy` and `Permissions-Policy`.
4. WHEN `curl -I https://<distribution-domain>/` is run, THE Distribution SHALL return the six headers listed in criterion 3.
5. WHEN `curl -I https://<distribution-domain>/api/v1/health` is run, THE Distribution SHALL return the six headers listed in criterion 3.
6. WHEN a request to the Lambda Function URL is made directly without the `X-Origin-Verify` header, THE Origin_Guard SHALL respond with status 403.
7. THE Content-Security-Policy SHALL allow script, style and image sources from the same origin and SHALL allow `connect-src` to the same origin and to the value of `VITE_PAYMENT_API_URL`.

### Requirement 14: SPA routing through CloudFront

**User Story:** As a user, I want deep links and page refreshes to open the application, so that the SPA works on any route.

#### Acceptance Criteria

1. WHEN a request path has no file extension and does not start with `/api/`, THE SPA_Rewrite_Function SHALL rewrite the URI to `/index.html`.
2. WHEN a request path has a file extension, THE SPA_Rewrite_Function SHALL leave the URI unchanged.
3. WHEN `GET /some/deep/route` is requested on the Distribution, THE Distribution SHALL return the content of `index.html` with status 200.
4. IF `GET /api/v1/unknown-route` is requested through the Distribution, THEN THE Distribution SHALL return the JSON error from the API with a 4xx status and not the HTML of `index.html`.
5. THE Web_Bucket SHALL serve assets with hashed file names with `Cache-Control` of one year, and SHALL serve `index.html` with no caching.
6. THE Deploy_Pipeline SHALL build the Web_App and upload the build to the Web_Bucket with the cache-control values of criterion 5.

### Requirement 15: Public HTTPS environment (HU-17, base)

**User Story:** As an evaluator, I want to open a public HTTPS URL, so that I can verify the deployed environment.

#### Acceptance Criteria

1. WHEN the Deploy_Pipeline completes a run, THE Distribution SHALL serve the placeholder page at `https://<distribution-domain>/` over HTTPS with status 200.
2. WHEN the Deploy_Pipeline completes a run, THE Distribution SHALL answer `GET https://<distribution-domain>/api/v1/health` with status 200 and the body `{"status":"ok"}`.
3. WHEN a request is made over HTTP to the Distribution, THE Distribution SHALL redirect the request to HTTPS.
4. THE Infra_Code SHALL be stored in the repository so that the environment can be recreated from code.
5. THE Monorepo SHALL run `terraform apply` only inside the Deploy_Pipeline, only for a plan file created in the same approved job, and only after approval on the Production_Environment.
6. THE Monorepo SHALL NOT contain scripts or workflow steps that run `terraform destroy`.
7. THE Monorepo SHALL NOT allow agents to run `terraform apply`, `terraform destroy`, `git commit` or `git push`.

### Requirement 16: Cost control and budget alarm

**User Story:** As a developer, I want a budget alert at 1 USD, so that I learn about any unexpected charge before the evaluation.

#### Acceptance Criteria

1. THE Infra_Code SHALL define an AWS budget of 1 USD per month with a notification sent to an email address supplied by a Terraform variable.
2. THE Infra_Code SHALL trigger the Budget_Alarm notification WHEN actual spend reaches 80 percent of the budget and WHEN forecasted spend reaches 100 percent of the budget.
3. THE Infra_Code SHALL keep every provisioned resource within the AWS always-free tier, using DynamoDB provisioned capacity of at most 25 RCU and 25 WCU across tables and indexes.
4. IF the notification email variable is not provided, THEN THE Infra_Code SHALL fail `terraform validate` or `terraform plan` with a message that names the missing variable.

### Requirement 17: Observability

**User Story:** As a developer, I want request-level logs in CloudWatch without sensitive data, so that I can trace problems after deployment.

#### Acceptance Criteria

1. WHEN the API handles a request, THE API SHALL write one JSON log line with the request identifier, method, path, status code and duration in milliseconds.
2. THE API SHALL write no secret value, no `X-Origin-Verify` value and no payment token to any log line.
3. WHEN the Origin_Guard rejects a request, THE API SHALL write a warning log entry with the request identifier and the reason `missing_header` or `invalid_header`.
4. THE CloudWatch log group of the Lambda_Function SHALL retain logs for 7 days.

### Requirement 18: Repository workflow and history

**User Story:** As a developer, I want conventions enforced from the first commit, so that the repository shows a clean, reviewable history.

#### Acceptance Criteria

1. THE Monorepo SHALL provide a root `README.md` stub that states the project purpose, the repository layout and the commands for lint, type check, tests with coverage and build, written in English.
2. THE Monorepo SHALL provide a pull request template that asks for the user story id and the evidence of the Quality_Gates.
3. WHEN a commit message does not follow Conventional Commits, THE `.githooks/commit-msg` hook SHALL reject the commit.
4. WHEN the Forbidden_Words_Check finds a forbidden word in staged content, THE `.githooks/pre-commit` hook SHALL reject the commit.
5. THE spec tasks SHALL leave all `git commit`, `git push`, Bootstrap_Module apply and deployment approval actions to the Developer, and SHALL NOT include any task that runs `terraform apply` or `terraform destroy` from an agent.
6. THE Developer SHALL enable the repository hooks with `git config core.hooksPath .githooks` before the first commit.

### Requirement 19: Terraform bootstrap module

**User Story:** As a developer, I want a one-time bootstrap module that creates the state bucket and the GitHub trust, so that every later deployment runs from GitHub Actions without manual infrastructure steps.

#### Acceptance Criteria

1. THE Monorepo SHALL contain the Bootstrap_Module in `infra/bootstrap`, using local Terraform state with the AWS provider region set to `us-east-2`.
2. THE Bootstrap_Module SHALL create the State_Bucket with versioning enabled, server-side encryption enabled and all four S3 public access block settings enabled.
3. THE Bootstrap_Module SHALL NOT create the GitHub_OIDC_Provider: it already exists in the account (created by the Developer). THE Bootstrap_Module SHALL reference it by its ARN `arn:aws:iam::<account>:oidc-provider/token.actions.githubusercontent.com`, built from the caller account id, without reading or managing it.
4. THE Bootstrap_Module SHALL create the Deploy_Role described in Requirement 20.
5. THE Bootstrap_Module SHALL accept the GitHub repository owner and name, and the State_Bucket name, as Terraform variables.
6. THE Bootstrap_Module SHALL output the Deploy_Role ARN and the State_Bucket name.
7. THE `.gitignore` SHALL exclude the local state files and the `.terraform/` directory of the Bootstrap_Module.
8. THE Bootstrap_Module SHALL pass `terraform fmt -check` and `terraform validate`.
9. THE Bootstrap_Module SHALL contain no secret values and no AWS access keys.

### Requirement 20: Least-privilege OIDC deploy role

**User Story:** As a security-conscious developer, I want the deploy role assumable only by this repository's deploy flow and limited to what it deploys, so that a compromised workflow cannot reach the rest of the AWS account.

#### Acceptance Criteria

1. THE Deploy_Role trust policy SHALL allow only the `sts:AssumeRoleWithWebIdentity` action from the GitHub_OIDC_Provider.
2. THE Deploy_Role trust policy SHALL require the `aud` claim to equal `sts.amazonaws.com`.
3. THE Deploy_Role trust policy SHALL require the `sub` claim to equal `repo:<owner>/<repo>:ref:refs/heads/master` or `repo:<owner>/<repo>:environment:production`, and SHALL accept no other `sub` value.
4. THE Deploy_Role permission policy SHALL allow only actions on S3, CloudFront, Lambda, DynamoDB, SSM Parameter Store, IAM, CloudWatch Logs and AWS Budgets that Terraform and the Deploy_Pipeline need for the resources of Requirement 12 and Requirement 16.
5. THE Deploy_Role permission policy SHALL limit S3, DynamoDB, SSM, Lambda and CloudWatch Logs actions to resources whose names use the project prefix, and SHALL limit IAM actions to the roles and policies of the Lambda_Function.
5a. THE Deploy_Role permission policy SHALL limit SSM write actions to the Origin_Verify_Secret parameter and SHALL grant no action on the Payment_Secret_Parameters.
6. THE Deploy_Role permission policy SHALL grant read and write access to the State_Bucket objects, including the lock file, and list access to the State_Bucket.
7. THE Deploy_Role permission policy SHALL NOT grant `iam:*` on all resources, `*:*`, or the permission to create access keys or IAM users.
8. THE Deploy_Role permission policy SHALL NOT grant any action on the Bootstrap_Module resources other than read and write access to the State_Bucket.
9. THE Deploy_Role SHALL have a maximum session duration of one hour.
10. THE Monorepo SHALL store no long-lived AWS access key in GitHub secrets, variables or files.

### Requirement 21: Deploy workflow

**User Story:** As a developer, I want a GitHub Actions workflow that deploys infrastructure, API and web after a merge, so that the public environment updates without commands from my machine.

#### Acceptance Criteria

1. WHEN the CI_Pipeline completes successfully for a push to `master` in this repository, THE Deploy_Pipeline SHALL run (`workflow_run` trigger), and SHALL NOT run for CI runs triggered by pull requests or from forks.
2. WHEN the Developer triggers `workflow_dispatch` on the Deploy_Pipeline, THE Deploy_Pipeline SHALL run.
3. THE Deploy_Pipeline SHALL declare the job permissions `id-token: write` and `contents: read` and no other permission.
4. THE Deploy_Pipeline SHALL declare a `concurrency` group so that two deployments never run at the same time, and SHALL NOT cancel a deployment that is already applying.
5. THE Deploy_Pipeline SHALL authenticate to AWS with the Deploy_Role ARN and the AWS region from the Deploy_Variables, using OIDC and no access keys.
6. THE Deploy_Pipeline SHALL run, in this order, `terraform fmt -check`, `terraform init` with the State_Bucket from the Deploy_Variables, `terraform validate` and `terraform plan`, and SHALL publish the plan as text in the job summary so the reviewer can read it before approving.
7. THE Deploy_Pipeline SHALL pass `budget_notification_email`, `payment_api_url` and the payment public key to Terraform from the Deploy_Variables.
8. WHEN the Production_Environment approval is granted, THE Deploy_Pipeline SHALL run `terraform plan -out=tfplan` and `terraform apply tfplan` inside the same approved job.
9. WHEN the apply finishes, THE Deploy_Pipeline SHALL install the API dependencies, bundle the API with esbuild, zip the bundle and run `aws lambda update-function-code` for the Lambda_Function.
10. WHEN the apply finishes, THE Deploy_Pipeline SHALL build the Web_App, upload the assets to the Web_Bucket with `Cache-Control` of one year, upload `index.html` with `Cache-Control: no-cache`, and create a CloudFront invalidation for the Distribution.
11. THE Deploy_Pipeline SHALL read the Lambda_Function name, the Web_Bucket name and the Distribution id from the Terraform outputs or the Deploy_Variables.
12. IF any step of THE Deploy_Pipeline finishes with a non-zero exit code, THEN THE Deploy_Pipeline SHALL stop and mark the run as failed.
13. THE Deploy_Pipeline SHALL contain no `terraform destroy` command, no secret values and no real payment credentials.
14. THE Deploy_Pipeline SHALL NOT print the Origin_Verify_Secret or any SSM parameter value in its logs.
15. THE Deploy_Pipeline SHALL NOT upload Terraform plan files, state files or `.terraform/` directories as workflow artifacts, because artifacts of a public repository are downloadable and plan files contain sensitive values in plain text.

### Requirement 22: Manual approval through the production environment

**User Story:** As a developer, I want a manual approval before infrastructure changes are applied, so that a merge cannot change my AWS account without my review.

#### Acceptance Criteria

1. THE Deploy_Pipeline SHALL run the apply, API deployment and web deployment jobs in the Production_Environment.
2. THE Production_Environment SHALL require at least one reviewer to approve the job before the job starts.
3. WHILE the approval of the Production_Environment is pending, THE Deploy_Pipeline SHALL run no `terraform apply`, no Lambda code update and no S3 upload.
4. THE Deploy_Pipeline SHALL run the `terraform plan` step before the approval gate so that the reviewer can read the plan in the run logs.
5. IF the reviewer rejects the approval, THEN THE Deploy_Pipeline SHALL end the run without changing any AWS resource.

### Requirement 23: Post-deploy smoke test

**User Story:** As a developer, I want an automatic check after every deployment, so that a broken deployment fails the run instead of going unnoticed.

#### Acceptance Criteria

1. WHEN the deployment steps finish, THE Deploy_Pipeline SHALL run the Smoke_Test against the Distribution domain.
2. THE Smoke_Test SHALL request `GET https://<distribution-domain>/` with `curl` and SHALL require status 200 and the six security headers of Requirement 13 criterion 3.
3. THE Smoke_Test SHALL request `GET https://<distribution-domain>/api/v1/health` through the Distribution with `curl` and SHALL require status 200, the body `{"status":"ok"}` and the six security headers of Requirement 13 criterion 3.
4. THE Smoke_Test SHALL send no `X-Origin-Verify` header itself, so that the check proves that CloudFront adds the header.
5. THE Smoke_Test SHALL retry each request up to 5 times with a 5-second delay between attempts to allow the CloudFront invalidation and the Lambda update to propagate.
6. IF a Smoke_Test request returns a status other than 200 or lacks one of the six security headers after the last retry, THEN THE Deploy_Pipeline SHALL mark the run as failed and print the name of the failed check.

### Requirement 24: Initial manual setup documentation

**User Story:** As a developer, I want a documented one-time setup, so that I can enable automatic deployments in my AWS account and GitHub repository without guessing.

#### Acceptance Criteria

1. THE Monorepo SHALL document in `docs/` the ordered one-time setup steps in English.
2. THE documentation SHALL describe how to run the Bootstrap_Module with `terraform init`, `terraform plan` and `terraform apply`, and how to read the outputs.
3. THE documentation SHALL describe how to create the Production_Environment with required reviewers.
4. THE documentation SHALL list every Deploy_Variable with its name, where to set it (repository or environment) and where to obtain its value.
5. THE documentation SHALL describe how to trigger the first Deploy_Pipeline run and approve it.
6. THE documentation SHALL describe how to create the three Payment_Secret_Parameters with `aws ssm put-parameter --type SecureString` before the first deployment, and how to update them later with `--overwrite`.
7. THE documentation SHALL state that the Developer never stores real payment secrets in GitHub, in Terraform files or in the repository.
8. THE documentation SHALL state that the Bootstrap_Module local state file must be kept by the Developer outside git.
9. THE documentation SHALL describe how to run the Smoke_Test commands manually to verify the environment.
